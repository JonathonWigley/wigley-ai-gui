Decisions: Only this module writes through `RoomStore` (plan.md § Boundary rules). The clock and claim ids come from `deps.clock` and `deps.randomHex`, which task 08 fills from `api.services` (AGENTS.md § An ambient service).
           `limits()` is read at each call, so a settings change applies to the next post. Task 08 fills it from the plugin settings `bodyCap` 1500, `postsPerMinute` 10 and `claimMinutes` 30 (plan.md, agent-decided).
           `participants(room)` returns the main agents of the room's live sessions and `USER_PARTICIPANT`. Task 08 fills it from the session rows and their titles. A subagent is never a target of `to` (design.md § The model: agents address each other by session title).
           Per room, `post`, `postHuman`, `addEntry` and the `unread` read (with its cursor update) run one at a time in call order, through one `createSerialQueue()` per room, so each guard sees every earlier post.
           **Post: checks in this order.** The first check that fails returns `{ ok: false, reason }` and writes nothing:
           1. `kind` is one of `POST_KINDS`. An entry kind is refused: `<kind> is an entry the app writes; post one of <the nine kinds>`.
           2. Idempotency: an earlier message in the room with the same `participantKey(from)` and the same non-null `key` returns `{ ok: true, id: <that id>, thread: <that message's thread>, duplicate: true }` and writes nothing. This check runs before every check below, so a retry of an accepted post always returns the first id, even when a later check (an `answerBy` that has since passed, the rate cap) would now refuse it.
           3. `body` trimmed is not empty, and its length is at most `limits().bodyCap`. Over the cap the reason is `body is <n> characters, over the cap of <cap>: put the content in a file and post its path with a short summary` (design.md § Guards).
           4. Each `refs` item has a `type` of `file`, `branch`, `commit`, `plan` or `message`, and a `value` that is not empty after a trim.
           5. `replyTo`, when set, names a message id in the room. An `answer` must set `replyTo`.
           6. A `question` names at least one target in `to`. `answerBy` and `onNoAnswer` are refused on every other kind. `answerBy` must be later than `clock.now()`; a value equal to now is refused.
           7. Each `to` name matches, after `trim().normalize('NFC').toLowerCase()` on both sides, the `name` of exactly one participant from `participants(room)`. No match or more than one match is refused: `no participant named "<name>"` or `"<name>" names <n> participants`, then `; the room holds: <names, comma-separated, in participants order>`. The names `you` and `system` follow the same rule: `you` matches the user participant, and `system` matches nothing. A name that matches the sender's own main agent (same `participantKey`) is refused for an agent sender: `you cannot address yourself`. Two names that match one participant collapse to one: the stored `to` holds each participant once, in the order of first appearance.
           8. Thread (see below) is valid.
           9. Identical body: an earlier non-entry message from the same `participantKey(from)`, with the same `body`, whose `at` is less than 2 minutes (120000 ms) before now, is dropped and returns `{ ok: false, reason: 'dropped: the same body was posted as #<id> <s> seconds ago' }`.
           10. Rate cap: when the sender already has `limits().postsPerMinute` non-entry messages with `at` greater than now minus 60000 ms, the post is refused: `rate cap: <cap> posts a minute; wait <s> seconds`, where `<s>` is the seconds until the oldest of those leaves the window, rounded up.
           Steps 9 and 10 apply to agent and mirror senders only. `postHuman` skips them: the user is not capped. Steps 9 and 10 count only non-entry messages (kinds in `POST_KINDS`). Entries are written by the app, so a lead that dispatches ten workers in a minute is not throttled.
           The guards read the room's messages through `store.read(room, 0)`. They keep no state of their own.
           **A failed save.** When `store.append` rejects, `post` and `postHuman` return `{ ok: false, reason: 'could not save the message: <error>' }`. Nothing runs after it: no thread reopen, no fan-out. `addEntry` rejects with the error, and runs nothing after it either. Task 08 catches that rejection.
           **Thread.** An explicit `thread` is trimmed and must be 1 to 80 characters with no line break; the trimmed value is stored. With `thread` null: the thread of the `replyTo` message when `replyTo` is set; else `session:<from.rowId>` for an agent sender; else `general`. Task 08 passes `thread` null when the agent omits it, so this default applies.
           A post (not an entry) into a resolved thread opens the thread again, after the append succeeds.
           **Stamping.** `at` is `clock.now()`. `to` holds the matched participants. `post` sets `userWord` false. `postHuman` sets `from` to `USER_PARTICIPANT` and `userWord` true, so an agent cannot forge the user's word (design.md § The user in the room). `PostRequest` has no `userWord` field.
           **Mirror human input.** `addMirror` hears the mirror's `onHumanMessage(room, thread, body)` and posts a `note` from `{ kind: 'mirror', rowId: null, agentId: null, mirrorId: mirror.id, name: 'you via <mirror.id>' }` into that thread, through the same checks as `post`, with `userWord` equal to `mirror.verified`. An unverified mirror's post is information only (design.md § Mirrors). A refused mirror post is logged as `mirror <id> post refused: <reason>`.
           **Entries.** `addEntry` runs no check and no guard. A body longer than `limits().bodyCap` is cut to `bodyCap - 1` characters plus `…`. `to` is `[]`, `userWord` false, the other fields null. An entry never opens a resolved thread.
           **Fan-out.** After each successful append (post, human post, mirror post, entry), the service starts the fan-out before the call resolves, and does not await it: it calls every `onMessage` listener with the new message, in registration order, then each registered mirror's `publish`, except the mirror the message came from. A `publish` that hangs never delays the post. A listener that throws is logged as `message listener failed: <error>`. A `publish` that rejects is logged as `mirror <id> publish failed: <error>`. The post still succeeds in both cases. `settled()` also waits for every in-flight `publish`. The disposable from `addMirror` stops the mirror's publish and disposes its `onHumanMessage` subscription.
           **Read.** A reader's cursor is the last message id it read in a room, 0 when none. `cursors.json` in plugin data holds `{ "<room>": { "<participantKey>": <id> } }`.
           `unread` returns the messages above the cursor that are not entries, not `progress`, not from the reader (same `participantKey`), and either name the reader in `to` (same `participantKey`) or sit in an open thread the reader takes part in. A reader takes part in a thread when it posted a non-entry, non-`progress` message there or a message there names it in `to`. An entry or a `progress` the reader wrote never makes it take part. A main agent (`agentId` null) always takes part in `session:<rowId>`. Then the cursor moves to the highest id of the snapshot the filter ran on, not the store's highest id at write time. The read and the cursor update run in the room's queue, so a post made meanwhile lands after the cursor and shows in the next read. `text` is the first non-blank line of the body, cut to 200 characters with `…`.
           **The user's reads.** The user reads in the viewer one thread at a time, so the user has a cursor per thread: `user-cursors.json` in plugin data holds `{ "<room>": { "<thread>": <id> } }`. `userUnread(room)` returns the room's messages above their thread's user cursor that are not entries, not `progress` and not from `USER_PARTICIPANT`, in id order. A message in a resolved thread counts. `markUserRead(room, thread, upToId)` sets that thread's cursor to `upToId` when it is higher. Task 08 builds the viewer's counts from these. The user is never an agent reader, so `read` and `cursors.json` never hold the user.
           `thread` returns every message of that thread whole, entries and `progress` included; for `thread` and `message`, `ReadItem.text` is the whole body. `message` returns one message whole; an id not in the room is refused `no message #<id> in <room>`. Neither moves the cursor.
           `ReadItem.from` is the sender's `name`; `ReadItem.to` is the targets' names.
           `unreadAddressed` returns the messages above the cursor that are not from the reader, are not entries and are not `progress`, and either name the reader in `to`, or have `userWord` true and an empty `to` and sit in a thread the reader takes part in (the "takes part" rule of `unread`). The second case is the user's word to a thread: a post from `you` in the viewer, or from a verified mirror. It has the same kind exclusions as `unread`, so the hook count, the pending wake check and `chatroom_read` agree. It does not move the cursor. Task 08 uses it for the hook line, the idle send and the pending wake check (design.md § Delivery).
           **Threads.** `threads.json` in plugin data holds `{ "<room>": ["<resolved thread>", …] }`. `threads(room)` returns one summary per thread that holds a message, ordered by `lastId`, newest first. `resolveThread` adds the thread to the list. A thread with no message, or an unknown room, is added the same way and throws nothing; `threads(room)` still lists only threads that hold a message. No agent tool resolves a thread in this plan; the viewer (task 09) is the caller.
           **Claims.** `claims.json` in plugin data holds every live claim of every room as a `Claim[]`. A claim with `expiresAt` at or before now is dropped at each read or write of the claims.
           `claim` validates: `reason` trimmed not empty; `minutes` null or a finite number above 0; a `paths` target holds at least one path, each made by `normalizeClaimPath`, and a null result refuses the claim (`<path> is not a repo-relative path`); a `branch` or `resource` is not empty after a trim.
           `expiresAt` is now plus `(minutes ?? limits().claimMinutes) * 60000`.
           A `paths` target is stored sorted in plain string order (`<`) with duplicates removed.
           Renew: when the holder (same `participantKey`) already holds a claim in the room with an equal target (same kind; stored `paths` lists equal; branch or resource equal), the claim keeps its id and gets the new `expiresAt`, `reason` and `holder`: the holder becomes the caller's current participant, so a retitled session gets its new name. `claims` and `claimsTouching` return the stored claim as is, so its holder `name` can lag until the next renew. Task 08 prints that name. Else the new claim gets the id `randomHex()`.
           Overlap: two targets overlap when both are paths and `claimPathsOverlap` is true, both are branches and equal, or both are resources and equal. Targets of two kinds never overlap. `overlaps` and `claimsTouching` list the live claims in the room that overlap the target, held by another session: a claim whose `holder.rowId` equals the asker's `rowId` is left out, so a lead and its workers never warn each other.
           `release` with an id ends that claim; an id held by another participant is refused `claim <id> is held by <name>`; an unknown id is refused `no claim <id>`. `release` with null ends every claim of the holder in the room. Claims are advisory and never block (design.md § Claims).
           `endClaimsOf(rowId)` ends every claim whose `holder.rowId` is `rowId`, in every room, and returns them. Task 08 calls it at the session's end.
           **Claim paths.** Claim paths are repo-relative and `/`-separated, so clones of one pool compare the same file (design.md § The model: a pool's clones share a room). Task 08 makes the hook's full paths repo-relative before it asks.
           `normalizeClaimPath` trims, turns `\` into `/`, collapses `//` to `/`, drops each `.` segment (a leading `./` and a `/./` inside), strips one trailing `/`, and returns null for an empty result, a lone `.`, an absolute path (leading `/` or a drive letter), or a path with a `..` segment. A directory claim `src/a` stays a literal: it overlaps `src/a/x.ts` only through a pattern such as `src/a/**`.
           `matchesClaimPattern`: a segment that is exactly `**` matches any number of whole segments, zero included; a `**` inside a longer segment (`src/**.ts`, `a**b`) acts as `*`; `*` matches any characters inside one segment; `?` matches one character that is not `/`; every other character matches itself. No braces and no classes. No glob library: the tree has none, and an install needs the user's yes.
           `claimPathsOverlap(a, b)` is true when any pattern of `a` overlaps any pattern of `b`. A pattern with no `*` or `?` is a literal. Two literals overlap when equal. A literal and a pattern overlap when the pattern matches the literal. Two patterns overlap when the part before the first `*` or `?` of one is a prefix of the same part of the other. This can warn on two patterns that share no file; a claim is advisory, so a false warning costs one question.
           **Files.** Cursors, threads and claims load at first use. A file that is missing reads as empty. A file that does not parse reads as empty and is logged as `<file> unreadable, starting empty`. A file that parses to a value of another shape reads as empty and is logged the same way. The shapes: `cursors.json` and `user-cursors.json` hold an object of objects whose values are integers; `threads.json` holds an object of string arrays; `claims.json` holds an array of whole `Claim` values. An entry of the wrong shape inside a right-shaped file is dropped, and the file is logged the same way. Each change writes the whole file through `files.write`, one write at a time per file through a `createSerialQueue()`. When a write rejects, the service logs `<file> not saved: <error>` and keeps the state in memory. `settled()` resolves once every queued append, file write and in-flight `publish` has settled, and never rejects.
